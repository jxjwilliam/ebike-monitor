## 0. 结论先行

1. **`oc_` 的结论更接近事实，`wb_` 的实现更接近落地。** 前者想清楚了"什么不能承诺"，后者想清楚了"具体怎么干"。两者不是竞争关系，是同一件事的两半。
2. **两套方案真正的分歧只有一个：10 分钟一张截图，能不能支撑"流入/流出"。** 其余分歧（工期、自动化、技术栈）都是从这一条派生出来的。`oc_` 的判断是对的，SOP 自己的 4 组对照也证明了这一点。
3. **架构差异的本质不是技术，是"谁当事实源"**：`wb_` 让 Celery 队列当事实源，`oc_` 让数据库当事实源。这一条决定了系统在崩溃、重跑、对账时是否可信。
4. **技术栈层面两套都没问题，都适合国内**；差别在复杂度顺序——`wb_` 太早做自动化，`oc_` 太早做企业级可靠性。首版只需要各抄一条：`oc_` 的"数据库是唯一事实源"，`wb_` 的"识别管道怎么搭"。
5. **最重要的一条建议在 §7.8**：南宁本地已经有政府侧的共享电单车智能监测系统在运行。这个事实比两份文档里的任何技术选型都更值得先查清楚——它可能意味着这个项目该"合作/采购"而不是"自研"。

### 2.1 我认为 `wb_` 最危险的一句话

> "改进后流入流出准确率 50% → 80%+"（`wb_03` §10.5、§12.3）

没有任何实验支撑，却写在目标准确率表里。一旦这个数字进入商务承诺，后面所有工期、报价、验收都会建在沙子上。

### 2.2 我认为 `oc_` 最容易被误读的一句话

> "首期用现场人工截图上传打通任务、质检、复核和交付"（`oc_00` §1）

这句话在工程上正确，但容易被听成"这事儿很简单"。真实情况是：**人工上传解决了"拿不到数据"的问题，没有解决"数据要多少人力"的问题**。960 个点位时段 × 3 品牌 × 7 轮，如果完全靠人，现场人力就是主成本，只是它不体现在服务器账单里。

## 3. 架构对比：一个是流水线，一个是账本

不做架构设计，只评价两套已有的。

| 关注点 | `wb_` | `oc_` | 我的评价 |
| --- | --- | --- | --- |
| 系统形态 | FastAPI + Celery + Redis + MinIO，采集/AI/校验三条队列 | 模块化单体 + 业务 API + 独立识别 Worker，Outbox 派发 | 量级都不大，**`oc_` 的分层更抗故障**；`wb_` 的三队列在当前规模是过度拆分 |
| 事实源 | Celery 队列与 `eta` 计划 | PostgreSQL 中的槽位、状态、版本 | **DB 为准**。队列丢了任务，系统还要能知道"这轮没采" |
| 任务模型 | 任务（task）→ 7 轮截图 | 计划槽位（slot）→ 多次尝试（attempt） | `attempt` 比"重试 3 次"更接近现实：同一时刻只能有一个获批证据 |
| 失败语义 | 失败→重试→ERROR | 11 个质量码 + 独立状态 | `wb_` 分不清"没采到"和"采错了"，验收时会被追问 |
| 证据管理 | 文件路径存 MinIO | 证据表 + SHA-256 + 对象版本 + 不可变 | **`oc_` 这条必须抄**，否则"可复查"无法举证 |
| 结果版本 | 直接改 `vehicle_data` | 结果 revision + 批准 + 冻结交付 | 涉及"谁改的、改前改后"，`oc_` 对 |
| 扩展路径 | Docker → K8s、实体机 → 云手机 | 单 ECS → 拆分部署 | 都太早。当前数据量一张 PG 足够，**不要把 K8s 写进首期** |
| 识别定位 | 核心模块，AI 产出即结果 | 辅助建议，人工复核后生效 | **`oc_` 的定位更安全**：AI 是建议器，不是裁判 |

### 3.1 我的取舍

只需要从 `oc_` 拿两条：

1. **数据库是唯一事实源**（槽位、状态、版本都落库，队列只传 ID）。
2. **证据不可变 + 摘要 + 版本化交付**（原图不覆盖，修订留痕）。

其余（Outbox、RabbitMQ、11 个质量码、角色分离、不可变交付包）可以在有第一个真实客户之后再加。反过来，`wb_` 的设备农场、账号池、反检测这三块，现在一块都不要做。

## 4. 技术栈对比：两套都能在国内跑，差别在"该不该现在上"

### 4.1 逐项对照与国内可用性

| 层 | `wb_` | `oc_` | 国内可用性 | 我的取舍 |
| --- | --- | --- | --- | --- |
| 管理前端 | React 18 + Ant Design 5 + Konva | Vue 3 + TS + Element Plus + ECharts | 两者都是国内 ToB 主流；Ant Design 与 Element Plus 的中文生态都很完整 | 按团队熟悉度选；**不要为了统一而换人**。Konva 的截图圈选能力两种栈都能用 |
| 采集端 | Airtest + ADB 真机 | 响应式 H5，二期 Kotlin | Airtest 是网易开源，国内资料多；H5 可直接跑在微信/企业微信里 | **先 H5**；Airtest 只做 PoC |
| 后端 | FastAPI + Python 3.11 | FastAPI + Python 3.12 | FastAPI 在国内数据/算法团队很常见；但国内 ToB 后端 Java/Spring 仍是主流 | 团队是 Python 就 FastAPI，是 Java 就 Spring Boot，**不影响方案** |
| 数据库 | PostgreSQL 15 + PostGIS | PostgreSQL 16 + PostGIS（阿里云 RDS） | 阿里云 RDS PG 支持 PostGIS，但**扩展版本随实例规格变化，必须实测**；腾讯云/华为云也有 | 用托管 RDS，别自建；PostGIS 版本在购买前验证 |
| 队列 | Celery + Redis | Celery + RabbitMQ + Outbox | Redis、RabbitMQ 国内都常见 | **首版可以都不要**：一张任务表 + 定时扫描足够；有并发压力再上 MQ |
| 对象存储 | MinIO 自建 | 阿里云 OSS + STS 直传 | OSS/COS/OBS 都是国内标准；MinIO 自建运维成本常被低估 | **试点可以用本地磁盘或 MinIO，生产直接 OSS**；STS 直传这条照抄 |
| OCR/CV | PaddleOCR + OpenCV + YOLOv8 | OpenCV + PaddleOCR + 可选检测模型 | PaddleOCR 是百度开源，国内部署无障碍；YOLO 系国内资料极多 | 先 OpenCV 基线，**YOLO 等标注量够了再上** |
| 视觉大模型 | 未涉及 | 百炼（境内推理核实）/ 自部署 | 通义千问 VL、混元、豆包都可用；**百炼要核实具体模型的推理部署范围，不能只看北京接入域名** | 首版不用；要用也只做"辅助建议"，且必须走境内推理 |
| 地图 | 高德 JS API | 高德 JS API 企业 Key | 两套都对。GCJ-02 与三家 App 一致，这是关键；百度地图也能用，Google 不可用 | 高德企业 Key，采购时确认**地图截图作为商业证据保存/转交**的许可 |
| 通知/协作 | 未涉及 | 钉钉（可选） | 钉钉、企业微信都是国内标准 | 首版甚至不需要，出问题先发邮件/群消息 |
| CI/制品 | GitHub Actions / GitLab CI | 阿里云云效 / 公司已有平台 | GitHub 在国内网络不稳；Gitee、Coding、云效更稳 | 用公司现有平台，**不要把构建依赖放在海外** |
| 部署 | Docker Compose → K8s | 单 ECS Docker Compose → 拆分 | 阿里云/腾讯云 ECS 均可 | **首版 Compose 单机**；K8s 不进首期 |

### 4.2 国内资源上要特别盯的三件事

1. **地图**：高德企业项目 Key + 商业许可。个人 Key 不能用于对外交付；截图作为证据保存和转交也要看条款。
2. **云视觉**：任何"云上大模型"都要确认**推理发生在境内**。`oc_05` 的研究是对的——接入地域 ≠ 推理地域。做不到就本地模型或纯人工。
3. **备案与数据**：对外提供网站要 ICP 备案；如果做小程序/App 还有相应备案；采集的图片、账号、设备日志按最小化处理。`oc_05` §3 已列，照做即可。

> 顺带一句：你说的"应该没有信创/等保要求"我按这个前提写。但即便没有，**数据不出境、日志可审计、密钥不落代码**这三条建议从第一天就做——它们几乎零成本，后期补很贵。

### 4.3 两套都没提、但国内项目常踩的坑

- **对象存储的图片预览**：不要生成长期公网 URL，用短时签名链接；日志里不要打印签名参数。
- **Excel 导出**：以 `= + - @` 开头的文本要防公式注入；空值不要格式化成 0（`oc_03` §5 提了，`wb_05` 没有）。
- **时区**：全部按 `Asia/Shanghai` 排班，库里存 UTC。`wb_` 的 `TIMESTAMP`（无时区）在跨时区协作时迟早出事。
- **手机与网络**：现场弱网、锁屏、来电、系统杀后台，是自动化采集的头号杀手；`wb_06` §7 提了但没量化。

## 5. 各自的优点

### `wb_` 的优点

1. **工程细节足**：三家 App 的入口、模板图清单、配准参数、训练脚本、Docker Compose 都写到了可抄的程度。
2. **SOP 映射清楚**：把人工步骤一步步对到代码（`wb_02` §7），这是把现场知识转成系统的正确姿势。
3. **问题诊断准**：`wb_03` §1.3 把流量误判拆成 4 个原因（边界偏移、图标同质、遮挡、刷新延迟），比很多方案都诚实。
4. **可视化好**：`wb_README` 的 8 张 Mermaid 图，讲得比大多数标书清楚。
5. **`wb_08` 有真调研**：MDS/GBFS 的对比、"中国平台不开放 GBFS"这个判断，解释了为什么必须走截图路线。
6. **成本意识**：MinIO 自建、真机试点、云手机后置，路线是省钱的。

### `oc_` 的优点

1. **口径严谨**：把"平台可见数、现场实际数、净变化、端点变化、真实流量、疑似调度"分开，这是本项目最重要的一次概念清理。
2. **证据链完整**：attempt、证据摘要、不可变原件、修订留痕、交付冻结，能回答"这个数字怎么来的"。
3. **可靠性设计到位**：数据库槽位、租约、幂等、Outbox、漏采状态，都是踩过坑才写得出的东西。
4. **边界诚实**：明确说"没有证据就标不可判定"，这在验收谈判里是护身符，不是软弱。
5. **国内落地研究扎实**：阿里云 RDS/PostGIS、OSS STS、百炼推理范围、ICP/App 备案、MediaProjection 限制，都查到了官方依据。
6. **决策门清晰**：P0–P4 每阶段有放行条件，尤其"P1 不通过就阻断"这条，能防止项目带着错误前提扩城。

## 6. 各自的不足

### `wb_` 的不足（按严重度）

1. **把假设写成结论**。自动化可行性、80% 流量准确率、4 周工期，三者都没有实验支撑，却写进了计划表。
2. **可靠性设计缺失**。Celery `eta` 预排 7 轮，broker 一重启计划就没了；没有槽位概念，也就无法区分"没采"与"没排"。
3. **坐标错误**。`GEOMETRY(POLYGON, 4326)` 存 GCJ-02（`wb_04` §2.1），等于对外谎称已转 WGS84。这个错误一旦进了交付包，很难解释。
4. **围栏判断被悄悄跳过**。`wb_03` §5.2 建议"整屏≈围栏"，直接把 100×100 米这个核心需求绕过去了。
5. **合规处理粗糙**。反检测（指纹修改、代理池）、API 逆向（Frida/JADX）、"截图即合规"，三处都需要业务和法务介入，不能由工程侧自行决定。
6. **错峰建议破坏可比性**。`wb_04` §1.3 让同城点位错开 5 分钟开始，这与"同一时段横向对比"直接冲突。
7. **数字不闭环**。500KB/张 vs 2MB/张、50px vs 170px 阈值、85%→95%，同一文档内互相打架。

### `oc_` 的不足（按严重度）

1. **对"怎么数"着墨太少**。项目核心难点是识别与匹配，`oc_` 只给了 OpenCV/PaddleOCR/可选模型，具体管道、阈值、失败恢复要靠 `wb_03`。这是它最大的空档。
2. **企业级设计偏早**。MVP 就要 Outbox + RabbitMQ + 11 个质量码 + 角色分离 + 不可变交付版本，对 2–3 人团队是负担，容易变成"先建平台，再采集"。
3. **人力成本没算透**。人工上传方案下，960 点位 × 3 品牌 × 7 轮的现场投入是主成本，文档只给了公式（`oc_04` §6），没有给出排班可行性和人力预算。
4. **文档密度过高**。决策者读不完，容易被当成"过度谨慎"而搁置；缺少一页纸的取舍建议。
5. **同样有未验证假设**。30 秒同轮极差、120 秒处理 SLA、720 台设备的峰值推算，都是估算，没有实测。
6. **商业视角弱**。没讨论报价结构、验收谈判、分期付款、甲方变更如何处理——这些在乙方项目里和代码一样重要。

## 7. 我的观点（核心）

### 7.1 口径：先签"计数 + 净变化"，端点匹配作加分项，真实流量写"不可判定"

验收口径未定，这是好事——还有谈判空间。建议按三档设计交付：

| 档位 | 交付内容 | 风险 | 适用情形 |
| --- | --- | --- | --- |
| A 基础 | 时点计数 + 净变化 | 低 | 甲方只关心"每个点有多少车、增减多少" |
| B 标准 | A + 端点流入流出（标方法与置信度） | 中 | 甲方能接受"端点口径"的说明 |
| C 完整 | B + 真实区间流量 | 高，需连续证据 | 甲方提供接口/视频，或愿意为现场连续采集付费 |

**建议按 B 报价、按 A 兜底。** 不要按 C 承诺。谈判时用一句话：*"前后都是 20 辆，只能确定净变化是 0；进来 8 辆又出去 8 辆，两张截图看不出来。"* 这句话比任何技术文档都有说服力。

### 7.2 架构：只抄 `oc_` 的两条，其余延后

- **数据库是唯一事实源**：任务槽位、状态、版本、证据都在库里；队列只传 ID。这一条几乎零成本，但决定了系统能不能对账。
- **证据不可变**：原图不覆盖、留 SHA-256、修订留痕。这是"可复查核验依据"这条甲方要求的唯一实现方式。
- **延后**：Outbox、RabbitMQ、K8s、11 个质量码、角色分离。等有真实客户和并发压力再说。

### 7.3 算法：先做 OpenCV 基线，别一上来训 YOLO

21 张样本训不出可靠模型，标注 300–500 张又要 1–2 周。更快的是：

1. 图标模板匹配 + 颜色/形状过滤，处理"同一位置多车"的聚集数字用 PaddleOCR 读；
2. 用 SOP 的 21 张人工结果算误差，先看基线到底差多少；
3. 只有当基线明显不够（比如遮挡严重、图标换版），再考虑 YOLO，并用真实截图标注。

**理由**：这个任务的背景干净、图标规则，传统 CV 的性价比通常被低估；而 YOLO 的收益要等到数据量足够才出现。

### 7.4 采集：先"人 + 支架 + 定时截图/录屏"，再谈 Airtest

自动化不是第一优先级，**稳定性**才是。首版建议：

- 一部手机 + 固定支架 + 定时截图（或整段录屏后抽帧），一个点位一小时，现场人员只负责切换 App 和确认；
- 同一台设备切换三品牌要先实测耗时，达不到 30 秒极差就改"一品牌一台设备"；
- Airtest 全自动只做 1 个点位 1 小时的 PoC，用数据决定是否推广。

**理由**：自动化能省的是"人力"，但它引入的"不可控失败"（App 更新、风控、登录态、定位漂移）在首版是最贵的东西。

### 7.5 技术栈：Python 单栈 + 托管 PG + OSS + 高德，别上 K8s

- 后端 Python（FastAPI）与算法同语言，值得保留；团队若以 Java 为主，换 Spring Boot，方案不变。
- 数据库用阿里云 RDS PostgreSQL + PostGIS，**购买前实测扩展版本**；不要自建 PG。
- 图片直接进 OSS，STS 直传；MinIO 只在完全离线时用。
- 前端 Vue 3 + Element Plus 或 React + Ant Design 都行，**看谁写**；地图只用高德。
- 首版不要：K8s、RabbitMQ、微服务、云视觉大模型、自建 OCR 集群。

### 7.6 团队与工期：2–3 人，6–8 周出可验收样包

- 4 周版：单点位 × 3 品牌 × 7 轮的全链路 + 5–10 个 Session 的计数盲测。
- 6–8 周版：一城 20 点的上传、质检、复核、导出跑通，给出分层误差报告。
- 8–10 周版（`oc_`）：加上多城准备、恢复演练、供应商培训。

**判断依据**：项目真正的长尾在"点位补齐 + 现场排班 + 异常处理"，不在写代码。这两件事都不随开发人数线性加速。

### 7.7 关于 `wb_08` 的 MDS/GBFS：思想可用，格式现在别兼容

- **值得借鉴的是思想**：MDS 的事件流（`status_changes`）恰恰说明"真实流量"需要事件级数据，而不是快照——这反过来支持 `oc_` 的口径判断。
- **现在不必兼容 MDS 输出**：甲方没要求，多一层映射只增加出错面。等有政府/平台客户明确要 MDS 时再做适配。
- **GBFS 那条结论是对的**：中国三家不开放标准 feed，所以只能自采。这个判断可以写进方案，用来解释为什么必须走截图路线。

### 7.8 最重要的一条：先查南宁已有的监测系统（build vs buy）

`wb_08` §3.1 提到，南宁已上线"AI + 大数据"的共享电单车智能监测系统，把淤堵点位从 30–40 个降到个位数，且监测对象同为美团/哈啰/青桔。

这条信息的分量超过两份文档里的所有技术选型：

- 如果该系统**对外开放数据或接口**，这个项目可能根本不需要自建采集，直接做"数据接入 + 分析 + 交付"更划算；
- 如果它由某家供应商建设，那么对方可能已有现成的采集能力和合规路径，合作比自研快得多；
- 如果只是政府内部系统、不对外，也值得了解它的点位划分和"淤堵"判定逻辑——那正是本项目要交付的东西。

**建议动作**：在写第一行代码之前，花 3–5 天做三件事——查该系统的建设方与招标公告、找南宁当地渠道打听接口能力、评估"接入/合作/自研"三条路的成本。这可能把 8–10 周变成 3–4 周。

### 7.9 关于两套文档的关系：不要合并

- `oc_01`–`oc_04`：契约层（指标、实体、API、验收）。改动要谨慎。
- `wb_02`/`wb_03`/`wb_06`：实现层（操作、算法、部署骨架）。可以大胆改。
- `cc_00`/`cc_README`：观点与决策记录。只增不改，保留判断过程。
- `wb_` 其余部分（`wb_01`/`wb_04`/`wb_05`/`wb_07`）：按 §3.1 取舍后使用，不要整份照抄。

合并成一份大文档会同时失去"可验收"和"可执行"两种属性。

### 7.10 我不建议做的五件事

1. **反检测、账号池、接口逆向**：不是技术问题，是授权问题。真要做，先拿到书面授权。
2. **承诺真实流入流出**：当前证据链支撑不了。
3. **首版上 K8s / 微服务 / 消息队列**：数据量远未到。
4. **一开始训练检测模型**：样本不够，先跑传统 CV 基线。
5. **把 4 周计划写进合同**：这是一个"能不能做出来"的探索，不是一个"做多久"的排期。

## 8. 由浅入深的实施顺序（每步都有可验收的产物）

| 步骤 | 做什么 | 产物 | 大致时间 |
| --- | --- | --- | --- |
| 0 | 用现有 7 个点位 + SOP 的 21 张图，人工数一遍并记录真值 | 一张误差对照表 | 1–2 天 |
| 1 | 一个上传页 + 一张证据表 + 一条完整性检查 | 能上传 21 张、能看出缺哪张 | 3–5 天 |
| 2 | 一个复核页（21 图切换、圈选、修订留痕）+ Excel 导出 | 单点可交付报告 | 1–2 周 |
| 3 | OpenCV 计数基线接入，产出分品牌误差与自动覆盖率 | 识别方案对比报告 | 1–2 周 |
| 4 | 一城 20 点的排班、异常、导出跑通 | 一城试点样包 | 2–3 周 |
| 5 | 真机自动化 PoC（1 点位 × 1 小时 × 3 品牌） | 自动化可行性结论 | 1–2 周，可并行 |

这条顺序的好处是：**每一步都能单独停下来交付**，不会出现"平台建完了但数不出来"或"数出来了但说不清怎么来的"。

## 9. 需要内部先定的问题

1. 这个项目我们是想**做产品**还是**做项目**？产品要抽象通用能力，项目只要尽快交付——两者取舍不同。
2. 甲方要的是**数据**还是**监测能力**？如果是后者，`wb_08` 里的南宁模式（政府侧平台）才是对标物。
3. 我们有没有**现场人力**？人工上传路线的前提是有稳定的人能按 SOP 执行，这比服务器更难保障。
4. 是否接受**"部分完成"的报告**？如果甲方要求"全部合格"，很多真实情况（漏采、遮挡、运营区外）就没法写进去。
5. 三品牌授权沟通由谁负责、什么时候启动？这件事的周期通常比开发长。

## 10. 一句话总结

> `oc_` 教会我们**不要承诺什么**，`wb_` 教会我们**具体怎么做**；首版只需要把 `oc_` 的两条底线（数据库是事实源、证据不可变）和 `wb_` 的一条管道（检测 → 配准 → 匹配）拼起来，然后用最土的方式（人 + 手机 + Excel）先跑通一个点位。至于 960 个点位、12 个城市、真实流量——等第一个点位能交付了再谈。
