# 项目总览：电单车多平台车辆分布数据采集系统

> 文档编号：wb_00  
> 创建日期：2026-10-30  
> 文档定位：项目全局视图，所有其他文档的入口

---

## 1. 项目背景

本项目为乙方（供应商）承接的共享电单车竞品数据监测项目。甲方需求方需要定期获取美团（MT）、滴滴（DD）、哈啰（HB）三家共享电单车平台在指定城市、指定时段、指定点位下的车辆实时分布数据，用于竞品分析和运营策略研究。

### 1.1 需求来源文件

| 文件 | 作用 |
|------|------|
| `XMF 数据采购需求沟通 1023.pdf` | 需求总纲：定义数据内容、量级、标准、验收要求 |
| `电单数车 线上测试点位 to 供应商.xlsx` | 测试点位清单：城市、点位名称、围栏经纬度（GCJ-02坐标系） |
| `电单车间断截图示例及执行SOP.xlsx` | 操作规范 + AI数车vs人工数车对照示例 |

### 1.2 需求核心参数

| 参数 | 值 |
|------|-----|
| 覆盖城市 | 12个 |
| 时段数 | 4个（如周中早高峰、周中晚高峰、周末早高峰、周末晚高峰） |
| 每城市点位数 | 20个 |
| 总点位数 | 12 × 4 × 20 = **960个点位** |
| 覆盖平台 | 3家（美团MT、滴滴DD、哈啰HB） |
| 单点位监控时长 | 1小时 |
| 采集间隔 | 每10分钟一轮 |
| 单点位采集轮数 | 7轮（T, T+10, T+20, T+30, T+40, T+50, T+60） |
| 单期总截图数 | 960 × 3 × 7 = **约20,160张截图** |
| 项目周期 | 长期，一个月一期 |
| 地理围栏 | 以停车点为中心的 100m × 100m 正方形 |
| 坐标系 | GCJ-02 |

### 1.3 每轮需采集的数据字段

每个品牌在每个时间节点的数据：

| 字段 | 说明 |
|------|------|
| 车辆数 | 当前时间点围栏内可见车辆总数 |
| 流入数 | 上一时间点到当前时间点，新出现在围栏内的车辆数 |
| 流出数 | 上一时间点到当前时间点，从围栏内消失的车辆数 |
| 疑似调度入 | 上一时间点到当前时间点，短时间内大量同向涌入的车辆数（推断为平台主动调度） |

## 3. 技术路线总览

### 3.1 推荐主路线：App自动化截图 + AI数车

```
                    ┌─────────────────────────────────────────┐
                    │            数据采集层                     │
                    │  Airtest + ADB + 多台Android测试手机       │
                    │  自动操控三家App → 定位到点位 → 截图       │
                    └────────────────┬────────────────────────┘
                                     │ 20,160张截图/期
                                     ▼
                    ┌─────────────────────────────────────────┐
                    │           AI数车分析层                    │
                    │  YOLOv8目标检测 + OpenCV图像比对          │
                    │  车辆计数 → 流入流出 → 疑似调度识别        │
                    └────────────────┬────────────────────────┘
                                     │ 结构化数据
                                     ▼
                    ┌─────────────────────────────────────────┐
                    │         任务调度与数据管理层              │
                    │  Celery + Redis + PostgreSQL + MinIO     │
                    │  任务编排 / 设备管理 / 数据存储 / 围栏判断 │
                    └────────────────┬────────────────────────┘
                                     │
                                     ▼
                    ┌─────────────────────────────────────────┐
                    │         数据校验与交付层                  │
                    │  异常检测 + 人工核对工具 + 报告生成        │
                    │  截图留存 → 质量校验 → 交付甲方            │
                    └─────────────────────────────────────────┘
```

### 3.2 辅助路线：API逆向探索（内部效率提升）

作为内部探索方向，逆向App网络请求获取结构化车辆数据。如果成功可大幅降低截图+AI数车的计算成本，但存在合规风险，不作为交付方案的依赖项。

### 3.3 选型理由

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 采集方式 | App自动化截图 | 与需求文档和SOP完全对齐，合规风险低，可提供截图作为验收依据 |
| 数车方式 | YOLOv8目标检测 | 当前性价比最优的目标检测模型，训练数据量需求适中 |
| 截图自动化 | Airtest | 网易开源，对中国App生态支持好，比Appium更稳定 |
| 后端语言 | Python | 全栈统一，算法/后端/调度一套语言 |
| 任务调度 | Celery + Redis | Python生态成熟，适合定时任务编排 |
| 数据存储 | PostgreSQL + MinIO | PostGIS支持围栏判断，MinIO存储截图文件 |
| API框架 | FastAPI | Python异步框架，性能好，自带Swagger文档 |
| 前端 | React + Ant Design | 生态成熟，快速搭建管理面板 |
| 部署 | Docker Compose（试点）→ K8s（规模化） | 试点阶段单机够用，规模化时平滑迁移 |

## 5. 核心风险矩阵

| 风险 | 概率 | 影响 | 缓解方案 |
|------|------|------|---------|
| AI流入流出准确率不达标 | 高 | 交付质量不通过 | 重点优化图像比对+多目标跟踪算法，保留人工核对环节 |
| App反自动化检测 | 中 | 采集任务中断 | 模拟真实操作行为，账号轮转，设备指纹多样化 |
| 账号被封禁 | 中 | 无法采集数据 | 多账号池管理，异常监控，快速切换 |
| 点位围栏与App显示不一致 | 中 | 数据范围偏差 | 围栏坐标校验工具，截图边界自动对齐 |
| 规模化时设备管理复杂度爆炸 | 低（试点后） | 运维成本高 | 云手机方案备选，任务调度自动化 |
| 合规风险 | 低（截图方案） | 法律风险 | 仅使用截图方案，不做接口逆向交付 |

## 6. 术语表

| 术语 | 含义 |
|------|------|
| MT | 美团（Meituan）电单车平台 |
| DD | 滴滴（DiDi）电单车平台 |

| 流出数 | 两时点间从围栏内消失的车辆数 |

| T~T+60 | 从起始时间到60分钟后的7个采集时间点 |
| GCJ-02 | 中国大陆标准加密坐标系（高德/腾讯使用） |
| SOP | Standard Operating Procedure，标准操作流程 |
