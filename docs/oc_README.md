# 电单车采集与核验平台：方案总览

日期：2026-10-30；状态：设计草案。

本文说明我推荐的架构、技术栈和实现顺序，作为 `oc_` 系列文档的统一阅读入口。当前仓库保存原始资料、方案和可视化，**尚未实现应用代码**；下文是设计建议，不是已经具备的系统能力。

## 1. 要实现的应用

面向美团、滴滴青桔、哈啰三家共享电单车，按指定城市、点位和时段采集车辆分布，经过质检与人工核验，交付能够复查的数据和证据。

原始要求为 12 城、4 时段、每时段各 20 点，每次观察一小时、每十分钟一轮，共七轮。一次点位时段任务包含三品牌共 21 个时点。每期各组合执行一次时，共 960 个任务、20,160 张截图；每月具体采集天数尚待确认。

第一版优先完成：**任务排班 → 人工截图上传 → 时空质检 → 辅助计数 → 人工复核 → 版本化交付**。同时验证授权数据接口，为后续自动化保留入口。

## 2. 架构：业务 API 加独立处理任务

推荐模块化单体后端与独立异步 Worker。业务规则集中管理，耗时的图像分析单独执行和扩容。现阶段先把采集与交付做可靠，再依据实际负载决定是否拆分服务。

| 模块 | 负责什么 |
| --- | --- |
| 管理与复核后台 | 项目、点位地图、排班、进度、图片对照、人工修订与交付审批 |
| 移动采集端 | 展示任务与参考区域，绑定七轮截图，上报漏采及运营区异常 |
| 业务 API | 权限、点位和区域版本、任务状态、上传授权、审核与审计 |
| PostgreSQL/PostGIS | 保存任务、结果、区域和版本，作为业务状态的唯一事实源 |
| 私有 OSS | 保存原图、原始接口响应、标注图和导出包；原件不被修订覆盖 |
| Outbox 与消息队列 | 将已提交业务事务可靠派发为异步任务，支持重试与恢复 |
| 识别 Worker | 文件校验、文字识别、画面配准、车辆图标检测与结果建议 |
| 交付模块 | 固定获批结果版本，导出数据、异常说明和证据清单 |

采集端先向 API 申请受限上传权限，再直接上传 OSS。API 校验文件后，在同一数据库事务中登记证据和 Outbox 事件；派发器将事件送入队列，Worker 幂等处理并保存建议。复核员修改结果，独立审核人批准后才生成正式交付。

这样既能避免图像分析阻塞上传，也能区分“图片已接收”“分析完成”和“交付已批准”。重复消息不会产生重复有效结果；模型失败可以重算，历史时刻漏采则必须保留缺失原因。

## 3. 技术栈与国内服务

| 层面 | 推荐选型 | 用途 |
| --- | --- | --- |
| 管理前端 | Vue 3、TypeScript、Vite、Element Plus、ECharts | 管理表格、审核界面和统计展示 |
| 采集前端 | 首期响应式 H5；二期按需增加 Kotlin Android | 先人工上传，后验证授权录屏、离线队列及设备管理 |
| 后端 | Python 3.12、FastAPI、Pydantic、SQLAlchemy、Alembic | API、校验、数据访问和数据库迁移 |
| 数据库 | PostgreSQL 16 与兼容的 PostGIS，生产优先阿里云 RDS | 业务数据、版本和空间查询 |
| 异步任务 | Celery、RabbitMQ、数据库 Outbox | 识别、质检和导出任务 |
| 图像分析 | OpenCV、PaddleOCR；按需训练专用图标检测模型 | 地图配准、提示文字识别和车辆计数 |
| 视觉模型 | 满足境内推理条件的百炼模型，或境内自部署模型 | 提供辅助分析，效果通过项目样本验证 |
| 地图 | 高德 JS API 企业项目 | 展示 GCJ-02 点位和监控区域 |
| 云与部署 | 阿里云 ECS、OSS、RAM/STS、KMS；Docker Compose、Nginx | 国内运行、私有证据存储、限权上传和密钥管理 |
| 监控与测试 | 日志服务或 Prometheus/Grafana；pytest、Playwright | 异常监控、业务规则测试和端到端验证 |

三品牌官方 App 或有权供应商提供的数据，是采集来源；高德用于地图展示，不能代替品牌车辆库存接口。钉钉通知、专用标注平台和企业设备管理可按实际规模补充。

“国内方案”要求业务、证据、备份和推理链路满足中国内地运行与数据约定，不代表全部组件均为国产；信创、国产 CPU/GPU 或国密要求需另做兼容性验证。百炼等服务必须核实具体模型的推理部署范围，不能只凭北京接入域名判断。选型依据及待验证事项见 [第三方服务研究](oc_05_china_services_research.md)。

## 4. 数据与算法的边界

必须把以下结果分开保存和展示：

- **时点车辆数**：截图中平台可见的车辆数；现场实际车辆数另存。
- **净变化**：两个可比时点的车辆数之差。
- **端点流入流出**：两端车辆身份能够可靠匹配时，得到的可见变化。
- **真实区间流入流出**：需要完整事件流或能够覆盖边界的现场连续证据。
- **疑似调度入**：有补车迹象并经人工复核的结果，保留证据和判定规则。

例如，前后都是 20 辆，只能直接确定净变化为零，无法排除期间进来 8 辆又出去 8 辆。没有证据支持的真实流量填“不可判定”，不能用零或净变化替代。

点位原始坐标按 GCJ-02 保留。停车围栏、100×100 米监控区域和现场圈选范围分别管理；不能直接把围栏当监控区域，也不能把 GCJ-02 改成 WGS84 标签后混算。

## 5. 大致实现步骤

| 阶段 | 主要工作 | 完成标准 |
| --- | --- | --- |
| ① 明确口径 | 确认时段、区域、数据来源、流量定义、允许误差及保存期限 | 有一份可执行、可验收的任务规则 |
| ② 单点 PoC | 先选 2—3 个可工作的点，验证截图、同步、计数和人工真值 | 能交付一个完整小时样包，并说明哪些指标可得 |
| ③ 建立业务底座 | 实现权限、点位导入、区域版本、排班和七轮槽位 | 任务有明确负责人、时间与区域 |
| ④ 打通证据链路 | 实现 attempt、OSS 限权直传、摘要校验、异常和审计 | 每份证据都能准确关联任务，原件可追溯 |
| ⑤ 增加辅助分析 | 实现 Outbox、Worker、OCR、配准和车辆计数建议 | 分析可重试，低质量图片进入人工复核 |
| ⑥ 完成审核交付 | 实现三品牌七轮对照、修订、独立批准和导出 | 交付值能追溯到原图、方法、区域和结果版本 |
| ⑦ 一城试点再扩城 | 验证并发、弱网、漏采、权限、备份恢复和成本 | 有实测报告及人机排班方案，再扩展至多城市 |

已有计划按约 8—10 个工程周安排 MVP、一城试点和扩城准备，这是人员与样本及时到位条件下的估算。品牌接口签约、备案和设备采购另计；Android 辅助采集、真实事件流和自动调度识别在 PoC 后单独估期。

第一条开发链路建议只覆盖：**导入一个点 → 生成一个 Session → 上传并校验证据 → 人工确认计数 → 批准并导出**。该链路跑通后，再接识别模型和多点并发，降低同时排查业务与算法问题的成本。

## 8. 实施前待确认事项

1. 四个时段的具体时间、每月采集日期和重复天数。
2. 每城四时段是否重复使用同一批停车点。
3. 真实流量还是端点变化，调度入是否包含在总流入中。
4. 三品牌数据来源、字段、授权范围、调用额度、保存及转交权利。
5. 监控中心、边界、时间容差、验收误差、保存期限及预算。

文档中的时间容差、性能、准确率、费用和工期均为**建议目标或测算假设**，须经 PoC 和业务确认后冻结。官方服务说明已联网核对，引用集中见研究文档；价格没有作为供应商报价核实。
